Steward 0.2.1 broadens Alibaba Cloud coverage, pins every Alibaba Cloud API call to official metadata, and closes several cleanup-safety gaps.

## Highlights

- **Alibaba Cloud coverage:** Steward now identifies 203 Alibaba Cloud resource types, 177 of which can be cleaned up (up from 139).
- **Official API contract:** Every Alibaba Cloud product API call is pinned to the metadata published at api.aliyun.com. Tests check each call's method, path and parameters, plus the list and read paths of every resource type, against the official response schemas and 286 official response examples.
- **Encryption key dependencies:** Resources encrypted with a KMS key are linked to that key. RDS, PolarDB and Redis encryption keys are read through the products' own encryption APIs. If a key cannot be read, the type's scan fails, so deleting the key stays blocked instead of looking unused.

## New Alibaba Cloud resource types

- **Load balancing:** ALB and NLB listeners and server groups; CLB virtual server groups, access control lists, server certificates and CA certificates.
- **Messaging:** Kafka topics and consumer groups; RocketMQ 4.0 and 5.0 topics and groups; RabbitMQ instances; EventBridge event buses and rules.
- **Containers and logs:** Container Registry namespaces and repositories; Simple Log Service logstores.
- **Networking:** SSL-VPN servers and client certificates; IPsec servers.
- **Monitoring and governance:** CloudMonitor application groups, alert rules, alert contacts and contact groups; Cloud Config rules and compliance packs.
- **Compute:** SAE applications and namespaces; EMR clusters; Elastic Desktop Service desktops, office networks and policies.
- **APIs:** API Gateway apps; Cloud-native API Gateway services and HTTP APIs.
- **Inventory only:** API Gateway APIs, Lingjun nodes, resource directory members, Cloud Config aggregators and WAF protected objects. These are listed but not deleted, for the reasons given in the Alibaba Cloud guide.

When you delete a parent resource, its children are deleted first, each as its own step with its own confirmation. This covers load balancer listeners, message queue topics and groups, and registry namespaces and repositories. Logstores and the rules inside a compliance pack are the exception: the parent's own delete removes them, and each is confirmed absent afterward.

## Cleanup safety

- A connection's own RAM groups and custom policies are now protected alongside its RAM user or role.
- KMS keys created by a cloud service are recognized from their creator. A key whose creator cannot be read is not deleted.
- Fixed MongoDB deletion-protection readback, which could report an instance as already gone.
- Several response paths that differed from the official schemas are corrected.
- Deletion is refused for subscription resources, default namespaces, system policies and service-synchronized groups.
- Batch delete APIs that report a failed item inside a successful response now fail the step.
- Missing-resource error codes such as `InstanceNotExist` are recognized. Codes about the account, service, product, region or user are not treated as a missing resource.

## Security

- VPN pre-shared keys and credential fields such as `TrustPassword` and `DomainPassword` are removed from stored raw records and from cloud API logs.

## Other changes

- `STEWARD_DB_MAX_CONNS` caps the PostgreSQL connection pool.
- Browser OAuth sign-in for Alibaba Cloud is hidden in cloud mode, where loopback callbacks cannot work.
- An empty VPC gateway endpoint list is no longer treated as an error.

## Upgrade notes

- Scanning the new types needs their read permissions. RDS, PolarDB and Redis key reads need `rds:DescribeDBInstanceTDE`, `rds:DescribeDBInstanceEncryptionKey`, `polardb:DescribeDBClusterTDE`, `kvstore:DescribeInstanceTDEStatus` and `kvstore:DescribeEncryptionKey`. RAM protection needs `ram:ListUsersForGroup` and `ram:ListEntitiesForPolicy`. KMS keys also need `kms:DescribeKey`.
- Run a complete scan after upgrading, so new relationships and protections apply before you plan any cleanup.
