Steward v0.2.0 greatly expands resource coverage for Microsoft Azure, Google Cloud, and AWS. It adds keyless OIDC connections for all four clouds, blocks cleanups that would remove access other resources still need, and adds a `steward update` command.

## Highlights

- **Much broader coverage:** Steward now inventories and plans cleanup for 491 Azure, 205 Google Cloud, 194 AWS, and 159 Alibaba Cloud resource types. For AWS and Google Cloud, that is up from 45 and 30 in v0.1.0.
- **Azure:** resource group and deployment stack cleanups remove their child resources in the right order and resume after interruptions. Covered services include AKS, Recovery Services and Data Protection backups, NetApp Files, Synapse, Elastic SAN, Azure Local and Arc, API Management, Batch, Kusto, Cosmos DB for MongoDB (vCore), AI Services and Foundry, AI Search, Redis, App Service, CDN and Front Door, Monitor, and Grafana. Microsoft Entra users and groups, Key Vault certificates, and management groups are inventoried read-only.
- **Google Cloud:** new support for Cloud Router, Cloud NAT and route policies, Hyperdisk storage pools, firewall policies, Cloud Identity groups, Infrastructure Manager, alerting, uptime checks, notification channels, dashboards, billing budgets, and Security Command Center settings. Instances, GKE, Cloud Run, and Cloud Functions are linked to the service accounts they run as.
- **AWS:** encrypted resources are linked to their customer-managed KMS keys. S3 buckets that still hold objects, object versions, or delete markers are protected.
- **Keyless connections:** connect AWS, Alibaba Cloud, Google Cloud, and Azure through OIDC workload identity federation instead of storing long-lived cloud keys.

## Safer cleanup

- Keys and identities that live resources outside the plan still use cannot be deleted, and neither can the credentials each connection itself uses.
- Deleting a KMS key's only administrator is blocked while the key exists.
- Deleting keys and identities requires a complete scan, so a partial inventory never looks like "nothing depends on this".
- Unresolved dependencies are saved with the plan. Errors meaning "resource in use" or "already gone" are recognized across providers.

## Command line

- **`steward update`** upgrades Steward through the method you installed it with: Homebrew, Scoop, APT, DNF, or a downloaded binary (replaced in place after SHA-256 verification). `steward update --check` only checks for a newer version.
- **Data lives in `~/.steward`** (`%USERPROFILE%\.steward` on Windows) no matter which directory you start from. Set `STEWARD_HOME` to use another location. `steward server status` and `stop` now work from any directory.
- The command line uses Chinese when your terminal locale is Chinese, and English otherwise.

## Upgrading from v0.1.0

1. Stop the server and back up your `.steward` directory. It holds the database and the credential key that unlocks your saved cloud credentials.
2. Upgrade with your package manager, or rerun the installer.
3. Move your data to the new default location, from the directory where you used to start Steward:

   ```sh
   mv .steward ~/.steward
   ```

   If you don't move it, Steward keeps using `./.steward` in that directory and reminds you at startup. Alternatively, set `STEWARD_HOME` to the existing directory.

4. Start Steward. Database migrations run automatically.

From v0.2.0 on, `steward update` handles future upgrades.
