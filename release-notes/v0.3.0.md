Steward 0.3.0 lets you connect Google Cloud, Microsoft Azure and AWS by signing in through the browser, and adds release checks that tell you about newer versions and security advisories.

## Highlights

- **Browser sign-in for every cloud:** Google Cloud, Azure and AWS connections can now be authorized by signing in through the browser, as Alibaba Cloud already could. Steward opens the cloud's own sign-in page, stores only the resulting tokens, and renews them automatically.
- **Release checks:** Steward asks `checkpoint.loomx.ai` once a day whether a newer release exists and whether a security advisory applies to the version you run. `steward version` shows the answer, any command shows an advisory, and a running server checks again daily.

## Browser sign-in

What each cloud asks for after you sign in:

- **Google Cloud:** pick one of the projects your account can reach.
- **Microsoft Azure:** pick one of the subscriptions your account can reach. The tenant comes with it.
- **AWS:** through IAM Identity Center. Enter your start URL and its region, sign in, then pick one of the accounts and roles you are assigned. AWS has no account-wide browser sign-in, so use an access key or OIDC if you don't use IAM Identity Center.

Two limits are worth knowing before you choose this path:

- **The browser and the Steward server must run on the same machine.** The cloud returns the authorization to `127.0.0.1`, so a server on a remote host cannot receive it. Use an access key or OIDC for remote deployments. Steward Cloud does not offer browser sign-in for the same reason.
- **The connection acts as you, not as a service identity.** It reads exactly what your account can read. On Azure, Steward obtains a separate token for each data plane, so one your account cannot reach, such as Key Vault or Microsoft Graph, is reported as failing while the rest of the inventory continues. A service account, service principal or access key remains the better choice for an unattended, stable scope.

If a sign-in is revoked, or the AWS client registration reaches its ninety-day expiry, the connection reports that authorization is required. Use **Replace credential** and sign in again.

## Release checks

A check sends four values and nothing else:

| Value | Example |
| --- | --- |
| Version | `0.3.0` |
| Operating system | `linux` |
| Architecture | `amd64` |
| Signature | a random UUID kept in `~/.steward/checkpoint_signature` |

The signature counts an installation once and keeps an advisory from repeating. It is random and is not derived from anything about you, the machine or the network. Your inventory, connections, credentials, scan results and the commands you run are never sent.

The answer is cached for a day, so a machine reaches the service at most once a day however many commands it runs. A check times out after three seconds and fails silently; nothing depends on it.

- `STEWARD_CHECKPOINT_DISABLE=1` or `DO_NOT_TRACK=1` turns checks off entirely.
- `STEWARD_CHECKPOINT_SIGNATURE_DISABLE=1` keeps checking but sends no signature.
- `steward update` still downloads from GitHub releases directly, so upgrading works with checks turned off.

## Security

- OAuth refresh tokens, client secrets, IAM Identity Center client secrets, service account JSON and Azure's per-audience tokens are removed from stored raw records and from cloud API logs.

## Other changes

- New `steward version` command prints the version and platform, and says when a newer release is available.

## Upgrade notes

- There are no database migrations. Existing connections keep working unchanged.
- Release checks are on by default. In an environment without internet access, a check gives up after three seconds without affecting the command; set `STEWARD_CHECKPOINT_DISABLE=1` to skip it altogether.
